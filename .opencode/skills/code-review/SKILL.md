# Код-ревью

## Роль ревьюера

Компилятор гарантирует безопасность памяти — ревьюер ищет то, что компилятор
не видит: ошибки бизнес-логики, неполные переходы состояний, гонки и деадлоки,
проглоченные ошибки, API, который легко сломать, и код, который тяжело
поддерживать. Ревью — это поиск реальных проблем, а не демонстрация стиля.

## Процесс

1. **Определи цель ревью.** Дифф текущей ветки (`git diff`, `git status`,
   `git log --oneline -10`), конкретный MR или путь. Если цели нет — спроси.
2. **Прочитай AGENTS.md.** Конвенции проекта меняют «правильное»: глобальные
   `LazyLock<Mutex<…>>` слоты, `Result<T, String>`, атомарные записи temp+rename —
   всё это осознанный выбор. НЕ предлагай «чистый» код, ломающий принятую схему.
3. **Собери и прогони тесты первым делом** (`cargo check`, затем
   `cargo test -- --skip spawns_java`). Ревью начинается с того, что код
   компилируется и тесты зелёные. Если не запускалось — честно пометь в отчёте.
4. **Пройди поток данных**, потом чек-лист ниже. На каждую категорию есть
   вопросы — не прочитывай файл заново для каждой, проход один.
5. **Отчёт** — по форме в конце: только реальные находки, по убыванию
   серьёзности, каждая с `файл:строка`, «почему это проблема» и конкретной
   правкой. Без придирок («переименуй переменную», «отформатируй иначе»).

## Чек-лист по категориям

### Логика и переходы состояний
- Граничные случаи: пустые списки, повторные клики/вызовы, отменённые и
  проваленные задачи, «версия не выбрана», превышение лимитов.
- Полнота переходов: все ли комбинации `LaunchStatus` × `Task` обработаны
  (Idle/Launching/Running/Error, busy→idle → rescan)? Есть ли «зависшее»
  состояние, из которого нет выхода?
- Побочные эффекты в функциях с read-only названиями; мутации, спрятанные в
  «проверках».

### Конкурентность (в этом проекте — потоки `std::thread`, async нет)
- Глобальные слоты `LazyLock<Mutex<Option<…>>>`: кто пишет, кто читает,
  не теряются ли результаты (`take()` vs `clone()`), не читаются ли они
  «мимо» слотов.
- `thread_local!` — ЗАПРЕЩЁН для межпотоковых данных (невидим другим потокам;
  классическая грабля этого проекта).
- Mutex: длинна ли критическая секция; удерживается ли блокировка во время
  блокирующего IO/сна/сетевого запроса; берётся ли лок в кадре UI.
- Порядок блокировок: не пересекается ли (нить A: X→Y, нить B: Y→X) — деадлок.
- `lock().unwrap()`: может ли мьютекс быть отравлен (panic в другой нити под
  локом) и убить приложение там, где достаточно ошибки?
- Процесс игры: `Child` опрашивается `try_wait()` без busy-loop; handle не
  дублируется и не теряется; убит/зареапен корректно.
- Согласованность снэпшота: берётся ли состояние один раз и дальше работает
  на копии, а не на «живом» мьютексе по частям? (не одна и та же гонка
  «прочитал-изменилось» внутри одного кадра).

### Обработка ошибок
- `unwrap`/`expect`/`panic!` в продакшн-коде (не в тестах) — оправдан ли
  каждый: инвариант действительно неубиваемый или это потенциальный краш
  пользователя?
- Потеря контекста: `map_err(|_| …)`, `let _ =`, игнорирование причины —
  читабельно ли сообщение для пользователя и хватает ли его для отладки?
- Ретраи: есть ли троттлинг (как 30 с у манифеста), нет ли бесконечного
  ретрая, что происходит после финальной ошибки?
- Атомарность: файлы пишутся temp+rename, а не напрямую (иначе — битый файл
  при обрыве).

### Производительность (глубокий разбор — в perf-review, здесь только явное)
- Клоны и аллокации в покадровом коде UI: `render()` вызывается каждый кадр —
  там не место `collect()`, `format!` в цикле, повторным парсингам.
- Повторные блокировки/запросы одних и тех же данных внутри одного кадра.
- `String::join` / конкатенация в цикле без `with_capacity` в горячем пути.

### Unsafe (в проекте сейчас нет — правило на будущее)
- Каждый `unsafe`-блок — `// SAFETY:`-комментарий: почему безопасно, какие
  инварианты обязан соблюдать вызывающий.
- `unsafe fn` — секция `# Safety` в док-комментарии, а не только в теле.

### API и дизайн
- Тип выражает намерение: `enum` вместо магических строк, `Option` вместо
  пустой строки-заглушки, `Result` вместо panic.
- Сигнатуры не провоцируют misuse: владельные аргументы там, где нужны только
  ссылки; короткие имена с смыслом; параметры в порядке, исключающем путаницу.
- Расхождение продублированной логики: одинаковые фильтры/парсеры в двух
  местах, которые уже начали жить по-разному.
- Мёртвый код: экспортнутое, но неиспользуемое; ветки, в которые нельзя
  попасть (проверить, действительно ли нельзя).

## Особенности проекта (проверять ВСЕГДА)

1. **Фоновые потоки → UI:** только глобальные `LazyLock<Mutex<Option<…>>>`
   слоты, НИКОГДА `thread_local!`.
2. **UI-кадр:** без аллокаций, клонов, дискового IO и сетевых запросов в
   `render()`/`ui()`.
3. **egui 0.36:** `Panel` вместо `TopBottomPanel`, `CornerRadius` вместо
   `Rounding`, панели принимают `&mut Ui`, `desired_width` — на билдере
   `TextEdit`. Кнопка «всегда enabled, чтобы ловить hover» — осознанное
   решение, не баг.
4. **Forge + BootstrapLauncher:** родительский jar НЕ добавляется в classpath —
   намеренно.
5. **Версия:** `version.json` и `APP_VERSION` синхронны при бампе; релиз
   выкладывается как ассет `mc-launcher.exe` (на него ссылается self-update).
6. **Таймауты скачивания:** 30 с на клиентские запросы, 20 мин на загрузку
   файла — менять их вместе, иначе крупные файлы (JDK) рвутся.
7. **Статус задач:** каждый фоновый поток обязан в конце выставить
   `Task::Done`/`Task::Error` — «молчащий» поток = зависший спиннер в UI.

## Async-код (в других проектах, не здесь)

Если ревьюится асинхронный Rust: блокирующие вызовы внутри async (стравляют
пул), удержание `std::sync::Mutex` через `.await` (деадлок), cancel-safety
(потеря данных при отмене фьючи), `spawn` без надобности vs `join!/try_join!`,
обработка `JoinHandle` (panic в таске ≠ тихая ошибка).

## Формат отчёта

```markdown
### Критично — <падение / потеря данных / невозможность выполнить сценарий>
- `файл.rs:NN` — проблема. → как исправить

### Предупреждения — <граничные случаи, гонки, скрытые ошибки>
- `файл.rs:NN` — проблема. → как исправить

### Замечания — <улучшения, не баги>
- `файл.rs:NN` — наблюдение.

Итог: N подтверждённых проблем (M критичных).
```

- Каждая находка — воспроизводимая: опиши сценарий, при котором она вылезает.
- Не писать «проверь-ка, может быть баг» — либо находишь сценарий, либо
  не упоминаешь.
- Язык отчёта — как в общении с пользователем (обычно русский), идентификаторы
  кода — как в исходниках.
