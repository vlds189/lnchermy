# Проверка версии релиза

## Роль

Хелпер, который не даёт выпустить релиз с неправильной версией. Это не
формальность: в истории проекта уже были (а) релиз с бинарником, собранным
ДО бампа версии (v3.0.8 выложил exe с APP_VERSION=3.0.7 — ассет удалялся и
заливался заново), (б) тег, который уже существовал на remote (v3.0.7) —
пришлось переименовывать в v3.0.8 на лету, (в) CHANGELOG с «v3.0.8+»,
не переименованный в конкретную версию.

## Процесс

1. **Прочитай AGENTS.md** — конвенции релиза этого проекта (review-gate перед
   release-сборкой, тест-exe с префиксом, пуш/тег/релиз через GitHub API).
2. **Установи фактические версии**, ничего не меняя:
   - `launcher-rust/src/state.rs` → `APP_VERSION` (строка ~7);
   - `version.json` (корень репо, поле `version`);
   - последний git-тег: `git tag --sort=-v:refname | head` (локальные) и
     **обязательно** `git ls-remote --tags origin` (remote!) — локальный тег
     может отсутствовать, а на remote уже быть;
   - последний опубликованный GitHub release (токен из
     `git credential fill`, как в репозиторном ритуале) через
     `GET /repos/vlds189/lnchermy/releases/latest`;
   - `docs/CHANGELOG.md` — все заголовки секций (нет ли `vX.Y.Z+`-плейсхолдеров);
   - `docs/**/*.md` — история изменений, «vX.Y.Z+»-заголовки.
3. **Проверь предлагаемую версию** по чек-листу ниже.
4. **Отчёт** по форме в конце. Если проверка не пройдена — версию исправить
   (или отказаться от релиза) до любых правок файлов.

## Чек-лист

- **Валидный семвер**: `X.Y.Z`, только цифры, без префиксов/суффиксов
  (`v3.0.12` — это тег, номер — `3.0.12`).
- **Строго выше всего**:
  - `APP_VERSION` в коде,
  - `version.json`,
  - последний локальный тег,
  - последний тег на **remote** (`ls-remote`),
  - последний GitHub release.
  Сравнение — покомпонентно по точкам (не строковое! «3.0.10» > «3.0.9»,
  но строковое сравнение его бы проигнорировало... вернее, «3.0.9» vs
  «3.0.10» строково неверно). Уже существующий на remote тег = релиз
  невозможен с этой версией.
- **Синхронность бампа**: `version.json.version` == `APP_VERSION` (после
  бампа). Поле `LastVersion` в settings — НЕ трогать.
- **Никаких плейсхолдеров**: в `docs/CHANGELOG.md` и истории изменений
  `docs/**` не должно остаться секций `vX.Y.Z+` — они переименовываются в
  конкретную версию релиза.
- **Бинарник собран ПОСЛЕ бампа**: если release-сборка была до правки
  `APP_VERSION` — она устарела, пересобрать. (Признак грабли: размер нового
  exe совпадает со старым релизом при ожидаемо изменившемся коде —
  проверить через self-update/вручную.)
- **Порядок релиза** (уже после прохождения проверки):
  бамп → релиз-сборка (review-gate: первый вызов блокируется, ретрай после
  code-review = подтверждение) → тест-exe пользователю → пуш main → тег
  + `git push origin <tag>` → GitHub release + ассет `mc-launcher.exe`
  → `curl -L …/releases/latest/download/mc-launcher.exe`: 200 и размер
  совпадает с локальным бинарником.

## Формат отчёта

```markdown
### Проверка версии <X.Y.Z> — вердикт: OK / ЕСТЬ ПРОБЛЕМЫ
- APP_VERSION: <текущее>; version.json: <текущее>; последний тег (remote): <тег>
- Результаты пунктов чек-листа: ok / ✗ <что не так, как исправить>
```

Каждый ✗ — воспроизводимый: укажи, где расхождение (формула версии или
файл) и что должно быть вместо. Язык отчёта — русский; версии и
идентификаторы — как в файлах.
